# Расширение «СайтПокупатели» для 1С:УНФ

Делает так, чтобы при загрузке заказов с сайта новые покупатели сохранялись в 1С
сами: физлицо, группа «Покупатели», тег «Конечный покупатель». Без этих реквизитов
рабочая база не записывает контрагента, поэтому мастер обмена сейчас их создавать
не может (проверено 20.11.2026: создание контрагента падало, выбран режим
«Не искать, подставлять выбранного»).

Решение клиента (Анна, 23–24.11.2026): карточка на каждого покупателя, физлицо,
группа «Покупатели», тег «Конечный покупатель», телефон — основной признак, email
должен попадать в базу.

Файл кода: `СайтПокупатели.bsl`.

## Что уже делает дедупликацию

Телефон как признак покупателя уже работает со стороны сайта: в выгрузке Ид
контрагента = `site-phone-<цифры>` (см. `exchange/1c_exchange.php`). Повторный
покупатель приходит с тем же Ид, и типовой обмен находит его карточку без нашего
кода. Расширение нужно для двух вещей:

1. **Заполнить обязательные реквизиты при создании** (физлицо, группа, тег) —
   основная задача, этап 1.
2. **Сопоставить с дублями, заведёнными вручную, по телефону** — этап 2, сложнее
   и рискованнее (меняет, к какой карточке привяжется заказ). Отдельно, после
   тестирования этапа 1.

## Перед установкой — проверить в их базе (3 пункта)

Код написан без доступа к базе и не скомпилирован. До установки нужно подтвердить:

1. **Можно ли вообще загрузить расширение в их 1С:Fresh.** База в облаке,
   Конфигуратор напрямую не открыть. Варианты: загрузить готовый `.cfe` через
   «НСИ и администрирование» → «Расширения конфигурации» (если сервис разрешает
   загрузку расширений этому пользователю), либо собрать расширение в
   Конфигураторе/редакторе EDT против копии базы. Нужно выяснить у клиента, что
   доступно. Это главный риск: без возможности грузить расширения вся затея
   отпадает и нужен другой путь (например, обработка контрагентов вручную после
   загрузки, или договориться о довыпуске права).
2. **Как в базе хранится тег «Конечный покупатель».** Открыть контрагента, у
   которого этот тег уже стоит, и посмотреть механизм (отдельный справочник
   «Теги» + табличная часть, или доп. реквизиты БСП). От этого зависит процедура
   `ДобавитьТег()` — сейчас это заглушка.
3. **Точные имена реквизитов контрагента:** вид физ/юр лица
   (`ЮридическоеФизическоеЛицо` и одноимённое перечисление) и что группа
   «Покупатели» существует именно с таким наименованием.

## Установка (когда пункты выше подтверждены)

1. Создать расширение конфигурации (режим «Расширение», а не изменение типовой).
2. Добавить **общий модуль** `СайтПокупатели` (Сервер), вставить код из
   `СайтПокупатели.bsl`.
3. Добавить **подписку на событие**:
   - Источник: `СправочникОбъект.Контрагенты`;
   - Событие: `ПередЗаписью`;
   - Обработчик: `СайтПокупатели.ПередЗаписьюКонтрагента`.
4. Дописать `ДобавитьТег()` по факту хранения тегов (пункт 2 выше).
5. Загрузить расширение в базу.

## Как проверить

На тестовых карточках (SVT-TEST-001..003 / НФ-00003806..808), не в бою:

1. Провести тестовый заказ с сайта с новым телефоном и email, запустить обмен.
2. Убедиться: контрагент создан, физлицо, группа «Покупатели», тег
   «Конечный покупатель», телефон `+7XXXXXXXXXX` и email на месте, заказ привязан.
3. Повторный заказ с тем же телефоном (в другом написании) → та же карточка,
   без дубля.
4. Проверить, что создание обычного контрагента вручную расширение не ломает:
   подписка срабатывает только для новой карточки без группы и заполняет значения
   по умолчанию; если сотрудник сразу указал группу — расширение не вмешивается.

## Границы (важно)

- Подписка срабатывает на любую новую карточку контрагента без группы, не только
  на обмен. Для таких карточек она проставляет физлицо + «Покупатели» + тег. Если
  это нежелательно для карточек, заводимых вручную, нужен более точный признак
  «это из обмена» (флаг в сеансе через перехват модуля обмена) — это усложнение,
  делать по решению клиента.
- `ДобавитьТег()` и `НайтиПоТелефону()` — заглушки до сверки с базой.
- Код не тестировался; первый прогон только на тестовых карточках.
